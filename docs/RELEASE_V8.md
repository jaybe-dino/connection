## 2. 빌드·배포

```bash
# 공용 자산 동기화(engine-live·v8 키트 → 각 앱 public, 캐시 버스팅)
bash scripts/sync-demo.sh
# 크리에이터·콘솔(정적)
(cd apps/creator-app && npx vite build)   # dist/ → app.theprlist.net (+ /products/)
(cd apps/console && npx vite build)       # dist/ → console.theprlist.net
# 관리자(React, 타입 검사 포함)
(cd apps/admin && pnpm build)             # dist/ → admin.theprlist.net (VITE_API_URL 미지정 = https://api.theprlist.net)
```

- **API 먼저**: 컨테이너 시작 때 `/app/db/migrations` 를 자동 적용해요(060–066, 모두 추가형). 이미지에 `db/migrations` 포함(8a5b4e2, SHA256 검증).
- 정적 앱은 API 배포 뒤에. 새 화면이 쓰는 엔드포인트가 이전 API 에는 없어요.
- 캐시 버스팅: 콘솔 `console-v8.js?v=20261101b`, 크리에이터 `creator-v8.js?v=20261101b`, 키트는 내용 해시.

## 5. TikTok 관련 테스트 분석

- 신규 크리에이터는 `require_onboarded` 에서 **프로필 + TikTok 소유 인증**이 있어야 가입(`/me/join`)·신청이 돼요.
- API 테스트는 로컬 가짜 제공자(`tiktok_connect`)로 OAuth 성공을 재현해요. 외부 호출은 없어요.
- E2E 에서 새로 만든 크리에이터 B(세션 격리 검수)는 실제 TikTok 인증을 할 수 없어요. 그래서 멤버십·신청 행을 DB fixture 로 넣었어요.
  - 검수 대상은 세션 경계이지 가입 게이트가 아니에요.
  - 가입 게이트 자체의 검증은 기존 테스트가 맡아요(`test_signup_launch_journeys`, `test_creator_auth_boundary_review`).
- 운영에서 키가 없으면 신규 가입은 ‘승인 대기’로 남아요.
  - 관리자 모집 화면은 `creatorEntryReady=false` 일 때 그대로 안내해요.
  - 실제 모집 전에 TikTok 승인 후 가입·신청 여정을 운영에서 한 번 확인해야 해요.

## 6. 이미지 검증 메모

- 제품 이미지:
  - 업로드는 2MB 이하를 스트리밍으로 받아요(초과 413).
  - 형식은 확장자가 아니라 매직 바이트로 JPEG/PNG/WEBP 만 받아요.
  - 저장은 DB bytea 예요.
- 노출 경로:
  - 브랜드·멤버에게는 HMAC 서명 URL(만료 포함)로 보여요.
  - 비로그인은 **공개 등록 중에만** 열려요(요청마다 다시 확인).
  - 서명 만료 시 화면이 목록을 다시 불러와요.
- 신규 제품은 사진을 먼저 고를 수 있어요.
  - 파일은 폼 메모리에만 있다가, 저장할 때 제품 생성 → 실제 업로드 순으로 처리돼요.
  - 업로드가 실패하면 같은 제품·입력·사진을 유지해 재시도해요.
  - 서버 성공 전에는 ‘저장했어요’를 띄우지 않아요.
- 가짜 제품 사진은 쓰지 않아요. 대체는 이니셜 그림(data:)이에요.
- API 이미지는 `db/migrations` 를 포함하고 SHA256 으로 검증했어요(8a5b4e2).

## 7. 고객 화면에서 뺀 내부 메모(여기에만 남김)

- 청구:
  - ‘주소 인증 완료 등록 크리에이터 수’ 기준은 **검토 중 정책**이라 계산에 쓰지 않아요.
  - 크리에이터별 과금 내역 표는 **서버 집계가 없어** 제공하지 않아요(월 청구서·금액은 기존대로).
- 팀: 캠페인별 담당 제한은 서버에 없어요. 운영자는 브랜드 전체 캠페인을 다뤄요(화면에도 사실대로 안내).
- 지원자 카드의 ‘운영팀 확인’은 `creators.verified`(운영팀 사람 검증)예요. TikTok 소유 인증과 다르고, 새 인증 판정은 만들지 않았어요.

## 9. 남은 항목·알려진 위험

- D06(분쟁 1차 응답·이의·총괄 최종 절차)은 이번 승인 범위 밖이라 그대로예요. 분쟁 화면은 실패 표시(D07)만 보강했어요.
- D10: 재제출 시 현재 값(`campaign_terms.revision_note`)은 비워지지만, 이전 링크·브랜드 수정 요청 메모는 버전별 `submissions` 행에 남아요.
  - 관리자 검수 현황에서 대기 건의 ‘이전 제출’과 ‘전체 이력(읽기 전용)’으로 확인해요.
  - 관리자가 먼저 검수해도 이후 브랜드 수정 요청·완료는 최신 버전에 기록되고, 관리자 검수 기록은 같은 행의 검사 목록에 남아요.
- 레거시 `POST /submissions`, `/submissions/{id}/review`, `POST /reports` 는 `AUTH_REQUIRED=1` 에서 관리자 전용 미들웨어로만 보호돼요.
  - 운영 값이 꺼지면 공개되므로 운영 설정을 유지해야 해요(기존 위험, 이번에 바꾸지 않음).
- 관리자 대리운영 전환 코드는 2FA 를 마친 관리자만 발급, 2분·1회용·해시 저장, 교환 시 활성 관리자 계정만 허용이에요.
  - 코드는 발급 당시 세션 세대를 저장하지 않아요. 발급 후 2분 안에 세션을 철회해도 계정이 활성이면 교환돼요.
  - 콘솔 출처가 `BRAND_CONSOLE_URL` 과 다르면 링크가 맞지 않아요.
