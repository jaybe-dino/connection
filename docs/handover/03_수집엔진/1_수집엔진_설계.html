01

목표와 설계 원칙

기존 발굴·수집 에이전트(붙여넣기·인바운드·소싱 스윕)는 정밀 저격이다 — 브랜드 프로필에 맞는 소수를 골라 초대한다. 이 엔진은 반대로 대량 저인망이다: 먼저 관련 있는 계정을 최대한 다 확보해 우리만의 크리에이터 원장(母 DB)을 만들고, 그 위에서 에이전트가 캠페인별로 저격한다. 母 DB가 크고 정확할수록 모든 브랜드의 CAC가 내려간다 — 이게 커넥션의 핵심 자산이다.

원칙내용
넓게 먼저, 걸러내기 나중수집 단계에서 과하게 거르지 않는다. 팔로워 1천 미만도 일단 담는다 — 영향력 스코어는 저장 후 계산.
계정 = 원자 단위영상·해시태그가 아니라 유니크 계정이 목표 단위. 중복 제거가 파이프라인의 심장.
다중 소스 교차한 소스에 의존하지 않는다. API가 막히면 다른 소스가 받친다. 같은 계정을 여러 소스가 확인할수록 신뢰도↑.
비용은 단가로 관리"비싸다"가 아니라 계정당 원가(CPA-collect)로 본다. 목표: 심화 포함 계정당 30~120원.
합법 경계 안에서공개 데이터 · 공식 API · 라이선스 DB만. 로그인 우회·비공개 데이터·CAPTCHA 무력화는 하지 않는다(§9).
母 DB와 에이전트의 관계 — 이 엔진이 채운 母 DB는 원장에 POOL 상태로 들어간다. 브랜드가 붙으면 에이전트가 母 DB에서 4축 판정 + 브랜드 프로필 매칭으로 후보를 뽑아 초대한다. 즉 수집(이 문서)과 판정(발굴·수집 에이전트)은 분리된 두 단계다.

03

수집 파이프라인 아키텍처

다섯 소스는 모두 하나의 파이프라인으로 흘러 母 DB에 수렴한다. 각 단계는 독립 워커 + 큐로 수평 확장한다.

Discover→Fetch Profile→Enrich(bio·email)→ Normalize→Dedup(아이덴티티)→Score(영향력)→母 DB (POOL)
단계하는 일기술
Discover소스별 커넥터가 계정 핸들/ID 후보를 발견. 결과는 handle만이라도 큐에 적재.소스별 어댑터 · 작업 큐(예: Redis/SQS)
Fetch Profile핸들 → 프로필 상세(팔로워·게시·bio·지역·링크). API 우선, 실패 시 다음 벤더로 폴백.벤더 라우터 · 프록시 풀 · 재시도/백오프
Enrichbio·link-in-bio·Linktree에서 이메일·왓츠앱·연락처 추출(§5). 국가 추정 보강.정규식 + 링크 크롤러 + 국가 룰
Normalize필드 표준화(팔로워 정수·국가 ISO·카테고리 태깅·언어).스키마 매핑
Dedup핸들·이메일·외부 링크·기기 신호로 동일인 병합. 母 DB의 유니크성 보장.아이덴티티 그래프 · 블로킹 키
Score영향력·활동성·카테고리 적합도·연락 가능성 점수 계산(§6).가중 스코어 → 나중에 ML
母 DB원장 POOL 상태로 저장. 소스·수집 시각·근거 함께.커넥터 → 4축 판정(에이전트)

母 DB 계정 스키마 (핵심 필드)

// creator_pool record { handle, platform_uid, display_name, country, // ISO2, IP·언어·bio에서 추정 category[], product_tags[], // 수집 축 followers, avg_views, engagement_rate, post_freq_30d, bio, links[], email, whatsapp, zalo, // 심화 influence_score, contact_score, // §6 sources[], // 어느 소스가 몇 번 확인했나 (교차검증) first_seen, last_refreshed, state: "POOL" // → 에이전트가 판정 후 승격 }
04

전수 수집 로직 — 제품 · 카테고리 · 국가별

"진행한 모든 틱토커를 제품·카테고리별로"의 핵심은 시드-그래프 수렴이다. 하나의 카테고리에서 씨앗을 심고 그래프를 넓히면 신규 발견이 0에 수렴할 때까지 돌려 사실상 전수에 도달한다. 국가는 이 루프를 병렬로 N개 돌리는 축이다.

4.1 수집 큐브 (축 3개)

국가

  • 태국 · 베트남 · 미국 · 인도네시아 · 일본 …
  • 축마다 언어·해시태그·채널이 다름 → 독립 파이프라인
  • 국가 추정: IP 리전 + bio 언어 + 해시태그 언어 + 전화 국번

카테고리 → 제품

  • 뷰티 › 선케어 › 선쿠션 처럼 트리로
  • 제품 노드마다 해시태그·키워드·경쟁사 태그 세트
  • TikTok Shop 카테고리 ID와 매핑 → L1 전수 통로

4.2 시드-그래프 수렴 알고리즘

for (country, category) in cube: seeds = hashtags[cat] + keywords[cat] + competitor_tags[cat] frontier = discover(seeds) // 씨앗 영상 → 작성자 seen = ∅ while frontier and new_rate > 3%: // 신규 발견률이 마르면 종료 batch = pop(frontier, 5000) accts = fetch_profiles(batch) for a in accts if a not in seen: seen.add(a); store_pool(a) // 母 DB 적재 frontier += commenters(a.top_videos) // 참여자 확장 frontier += related_users(a) // 추천 그래프 frontier += same_sound_authors(a) // 트렌드 확장 log(country, category, |seen|) // 이 셀의 전수 근사치
왜 전수에 수렴하나 — 한 카테고리에서 활동하는 계정은 서로 댓글·팔로우·같은 사운드로 촘촘히 연결돼 있다. 그래프 확장은 이 연결망을 타고 번지므로, 신규 발견률이 3% 밑으로 떨어지면 그 카테고리·국가의 활동 계정을 거의 다 담았다는 뜻이다. 남는 건 완전 고립된 신규 계정뿐이고, 그건 지속 수집(§8)이 매일 줍는다.

4.3 제품별 "진행한 모든 틱토커"

특정 제품을 실제로 다룬 계정을 전수로 잡는 3중 그물:

그물방법
① 커머스 그물 (L1)TikTok Shop Affiliate API로 그 제품/유사 SKU를 홍보한 어필리에이트 전량 — 판매 실적까지.
② 콘텐츠 그물 (L3)제품명·브랜드 태그·성분 키워드·박스 언박싱 해시태그로 영상 검색 → 작성자.
③ 참여 그물 (L3)①②가 만든 영상들의 댓글·저장·듀엣·스티치 계정 — 관심층까지 확장.

세 그물의 합집합을 dedup하면 "이 제품 생태계의 모든 계정"이 된다. 이걸 제품 노드에 product_tags로 태깅해 저장.

05

프로필 · 연락처 심화 (bio · 이메일 · 국가)

계정만으로는 접촉이 안 된다. 母 DB의 각 계정을 연락 가능한 리드로 승격시키는 심화 단계.

5.1 이메일 · 연락처 추출 3단

단방법 · 커버리지
① bio 직접 파싱bio 텍스트에서 이메일 정규식 + 왓츠앱/Zalo/라인 번호 + "협업 문의" 패턴. 즉시·무료. 커버리지 낮음(15~30%).
② link-in-bio 크롤Linktree·Beacons·개인 사이트를 따라가 연락 페이지의 이메일 추출. 커버리지 크게 상승. (전용 액터 존재)
③ 이메일 DB 조인influencers.club류 검증 이메일 DB와 핸들로 조인 — 자체 못 찾은 계정 보강. 유료·고커버리지.
# 이메일 추출 (bio + link-in-bio) EMAIL = r'[\w.+-]+@[\w-]+\.[\w.-]+' biz = extract(bio, EMAIL) or crawl_linktree(bio.links).emails if not biz: biz = email_db.lookup(handle) # 유료 폴백 record.email = verify_mx(biz) # MX·구문 검증 후 저장

5.2 국가 판정 (다신호 합의)

단일 신호는 틀린다. 4개 신호의 가중 합의로 국가를 확정하고 신뢰도를 함께 저장한다.

  • 계정 리전(공개 시) · bio 언어 · 해시태그/캡션 언어 · 전화 국번 · 주 활동 시간대
  • 불일치 시: 다수결 + 신뢰도 하향 → 심화 재검증 큐로
이메일 발송으로의 연결 — 추출한 이메일은 우리 문서의 실경로(Glovek/TopView 벌크 발송 → 링크트리/국가별 링크 → Zalo/왓츠앱 → 가입 → 캠페인 신청)로 흐른다. 발송은 반드시 OUTBOUND 게이트와 수신거부·재접촉 금지 규칙(발굴·수집 에이전트)을 거친다 — 母 DB에 있다고 바로 뿌리지 않는다.
06

영향력 스코어링 · 우선순위

"영향력을 최대한 감안해 최대한 뽑는다"는 수집은 넓게, 심화·접촉은 영향력 순으로 해석한다. 다 담되, 비싼 심화(이메일 DB 조인)와 접촉은 점수 높은 순으로 태운다.

6.1 영향력 스코어 (수집 후 계산)

신호의미
팔로워 · 팔로워 증가 곡선규모 + 성장세(계단형 급증은 가짜 신호로 감점)
인게이지율 (댓글·저장/팔로워)규모보다 중요 — 작아도 높으면 상위
평균 조회 · 조회/팔로워도달 효율
게시 빈도(30일) · 최근성살아있는 계정인가
카테고리 적합 · 커머스 실적제품 태그 일치 · Shop GMV(있으면)
연락 가능성이메일/연락처 확보 여부 → 접촉 우선순위

6.2 영향력 등급 → 처리 경로

등급대략 규모처리
Mega/Macro100K+이메일 DB 조인 전량 · 에이전시/1:1 우선 · 사람 검토
Mid/Micro5K~100K이메일 심화 · 자동 아웃리치 주력 (핵심 볼륨층)
Nano~5K母 DB 보관 · 인게이지 상위만 심화 · 커뮤니티/인바운드로
비용 배분 원칙 — 수집(Discover~Score)은 전 계정에 싸게 적용, 심화(이메일 DB)와 접촉은 영향력 상위부터 예산 소진까지. 목표 100만 계정 중 이메일 확보는 상위 20~30만이면 충분 — 나머지는 커뮤니티·인바운드로 자연 유입시킨다.

규모 · 비용 경제학 — 50만~100만 달성

7.1 볼륨 구성 (예시 배분)

소스기여 계정비고
L2 라이선스 스냅샷40만~60만국가×카테고리 필터 대량 확보 — 뼈대
L3 시드-그래프 (전수 수렴)20만~40만신규·롱테일·참여층 · 우리 고유 자산
L1 TikTok Shop/Research5만~15만커머스 실증 계정 · 고품질

L5 에이전시수천~2만완주 라벨 시드

7.2 단가 모델 (계정당 원가, 개략)

항목단가(개략)100만 기준
프로필 fetch (스크레이퍼)~$2 / 1,000 ≈ 3원/계정~300만원
L2 라이선스 스냅샷계약형(대량 할인)수백~수천만원 (협상)
이메일 심화(상위 25만)DB 조인·크레딧중간 비중
프록시·인프라·큐고정+가변월 운영비
블렌디드 목표 (심화 포함)계정당 30~120원
비용을 낮추는 지렛대 — ① L2 라이선스로 fetch 비용을 통째로 건너뛴다(가장 큼). ② L3 그래프는 우리가 직접 돌려 한계비용이 프록시·컴퓨트뿐. ③ 심화는 상위 등급만. ④ 母 DB는 한 번 채우면 모든 브랜드가 공유 — 브랜드가 늘수록 계정당 원가가 분모로 나뉜다. 이게 §10의 복리 효과.
08

지속 수집 (Continuous Listing) — 외부 영역 상시 파이프라인

1회 대량 적재로 끝이 아니다. 크리에이터는 매일 새로 생기고 지표는 매일 변한다. 상시 증분 루프가 母 DB를 살아있게 유지한다.

8.1 세 개의 상시 루프

루프주기하는 일
신규 발견매일카테고리별 신규 해시태그 영상·신규 어필리에이트·참여 신규 계정만 델타 수집. 이미 seen이면 스킵.
지표 리프레시7~30일기존 계정의 팔로워·인게이지·활동 갱신. 영향력 스코어 재계산. 죽은 계정 DORMANT 강등.
연락처 보강지속이메일 미확보 상위 계정 재시도(bio 갱신·새 link-in-bio). 반송·수신거부 반영.

8.2 트리거 · 채널 상시 모니터

  • 트렌드 트리거 — 급상승 해시태그·사운드 감지 시 즉시 해당 참여자 수집(트렌드 초기 진입)
  • 경쟁사 워치 — 경쟁 브랜드 태그·멘션 실시간 → 그들과 일한 계정 자동 적재
  • 커뮤니티 워치 — Facebook 그룹·Threads·Zalo의 신규 KOC 모집/자기소개 글 파싱(§L4)
  • 인바운드 상시 개방 — 공고→링크트리→왓츠앱/Zalo→폼 루트를 항상 열어두고 유입을 母 DB로
증분 루프델타 발견→변경분만 fetch→스코어 재계산→등급 이동→알림(트렌드·경쟁사)
비용 효율 — 지속 수집은 변경분(델타)만 처리하므로 초기 대량 적재보다 한 자릿수 싸다. 母 DB가 클수록 "이미 seen" 비율이 높아져 신규 발견 단가만 남는다.

플랫폼 ToS · 차단공식 API 우선 · 공개 데이터만 · 로그인 우회/CAPTCHA 무력화 안 함 · 상업 벤더 뒤에 리스크 위임 · 프록시 로테이션·레이트 준수

이메일 발송 규제OUTBOUND 게이트 · 일일 상한 · 도메인 워밍업 · unsub 의무 · 90일 재접촉 금지 (발굴·수집 에이전트가 집행)
데이터 신선도·정확도지표 리프레시 루프 · 소스 교차검증 횟수 저장 · MX 검증 · 죽은 계정 강등
벤더 종속다중 벤더 라우터 · 한 소스 실패 시 폴백 · L3 자체 그래프로 최소 생존선 확보
선 — 이 엔진은 공개 데이터 수집·공식 API·라이선스 DB까지다. 비공개 계정 내부, 로그인 세션 탈취, 봇 탐지 무력화는 하지 않는다. "비용이 들어도 최대한"은 합법 범위 안에서 벤더·프록시·심화에 돈을 더 쓴다는 뜻이지, 경계를 넘는다는 뜻이 아니다.
10

커넥션 연동 — 母 DB에서 캠페인까지

수집 엔진 → 母 DB (POOL)→발굴·수집 에이전트: 4축 판정 + 브랜드 프로필 매칭→ 초대 (OUTBOUND 게이트)→가입(OAuth) → 크리에이터 DB→셀 · 캠페인
연결점내용
母 DB → 후보 큐브랜드가 붙으면 母 DB에서 국가·카테고리·영향력·연락 가능으로 필터 → 발굴·수집 후보 큐에 적재.
4축 판정 재사용진짜 사람 / 제품 적합 / 협찬 과다 / 중복 — 母 DB 필드로 대부분 즉시 판정.
브랜드 프로필 매칭온보딩 학습 프로필(고객의 언어·성분·톤)과 계정 콘텐츠를 매칭해 적합도 점수.
학습 루프 환류초대→완주 결과가 母 DB 계정에 완주 라벨로 붙어, 다음 수집·판정 가중치를 갱신(L2 평가 하네스).
복리 효과母 DB는 전 브랜드 공유 자산 — 브랜드가 늘수록 계정당 수집 원가는 분모로 나뉘고 완주 라벨은 쌓인다.
한 줄 요약 — 이 엔진은 커넥션의 연료 탱크다. 발굴·수집 에이전트가 "누구에게 갈까"를 잘 판단하려면 그 앞에 충분히 크고 정확한 母 DB가 있어야 한다. 50만~100만 계정은 목적이 아니라, 모든 브랜드의 CAC를 구조적으로 낮추는 토대다.
