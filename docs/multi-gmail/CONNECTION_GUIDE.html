운영 구조

디노 공용 모집 → 회사 Gmail 선택 → 고객 브랜드·상품 선택 → 수신자 사전 검수 → 초안 승인 → 간격을 둔 발송 → 원래 계정으로 회신

회사 계정은 회사 공간에 연결합니다. 고객 브랜드를 제안 대상으로 선택하면 그 브랜드의 저장된 프로필·상품·가입 링크를 사용합니다. 고객 브랜드의 계정을 다른 브랜드 제안에 임의로 쓰지 않습니다. 같은 메일박스를 서로 다른 공간에 중복 연결하지 않습니다.

회사 모집 공간은 고객 가입 과금에서 제외합니다. 크리에이터가 실제 고객 브랜드에 가입하고 검증되는 기존 사용량·과금 모델은 유지합니다. 고객 가입 과금의 실제 계약과 사용량은 별도로 검토하며, 이번 개발로 결제나 새 카드 등록을 실행하지 않았습니다.

발송 기준과 OSMU

5개 계정이 모두 연결되고 중지·제공자 제약·기존 사용량이 없다면 시스템 총 상한은 최근 24시간 1,000건입니다. 한도 소진이나 연결 해제 시 다른 계정으로 자동 변경하지 않습니다. Gmail에서 직접 보낸 양은 이 시스템의 기록에 자동 포함되지 않으므로 같이 사용하는 운영자는 이를 별도로 조정해야 합니다.

모집 공간의 수신거부와 제안 고객 브랜드의 수신거부를 함께 확인합니다. 기존 90일 중복 차단을 유지하며 다른 브랜드 제안이라는 이유로 연락 제한을 우회하지 않습니다. 반복 제안은 상품 적합성·관계·수신 의사를 확인한 별도 검토 대상으로 운영합니다.

화면의 ‘Gmail 접수’는 제공자 메시지 ID 반환을 뜻합니다. 배달·회신·신청·참여 확정·배송·게시·판매는 별도 단계입니다. 캠페인 참가 수 합계, creator_id 기준 고유 수, 실제 사람 검증도 구분해야 합니다. 이번 단계는 월 3만 명 실운영 또는 하루 신규 1만 명 달성 완료를 의미하지 않습니다.

운영 반영과 인수 순서

  1. 운영 DB 백업과 현 배포 상태를 보관합니다. 새 발송 큐를 자동으로 재개하지 않도록 GMAIL_SEND_RESUME_ENABLED=0 유지 여부를 확인합니다.
  2. 검수 브랜치의 코드와 DB 마이그레이션 037~040을 검토 후 배포합니다. API /health의 커밋과 프런트엔드 새 기능을 대조합니다. 이번 턴에서 이 배포는 실행하지 않았습니다.
  3. 어드민 ‘디노 공용 모집 공간 생성’을 실행하고 기존 고객 브랜드가 내부 공간으로 변경되지 않았는지 확인합니다. 새 권한·인증정보를 자동 발급하지 않습니다.
  4. 기존 회사 발신 계정의 Google 권한 연결을 사용자가 확인하고 완료합니다. 저장된 암호화 키를 임의 변경하지 않습니다.
  5. 발신 계정·제안 고객 브랜드·실제 제품 조건·수신자·본문을 검토합니다. 사전 검수와 초안 저장만으로는 발송하지 않습니다.
  6. 수신자가 명시된 실시험을 별도로 승인한 후 접수·수신·회신·중지 동작을 확인합니다. 실계정 시험 성공으로 신규 1,000건 배치 전체가 승인된 것으로 간주하지 않습니다.
  7. 자동 재개는 승인 배치만 처리하도록 운영 설정을 별도로 확인합니다. 자동 재개가 꺼져 있으면 화면에 대기 안내가 표시됩니다.
